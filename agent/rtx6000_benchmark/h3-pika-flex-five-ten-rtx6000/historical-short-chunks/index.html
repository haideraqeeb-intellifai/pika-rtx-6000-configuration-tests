did not make this workload faster.

One resident transformer processed a real batch of two, with separate audio conditioning, anchors and random seeds. It reduced kernel launches, but the pair finished 2.5% slower than processing the chunks sequentially.

All three layouts feed the same one resident VAE, which decodes the two chunks sequentially after both denoises complete. This holds decoding constant and isolates the transformer comparison.

The existing H3 wrapper and fast attention code assume batch size one. The experiment adds a local adapter: linear/MLP operations combine both chunks’ token rows, while attention keeps a separate batch axis so tokens cannot attend across chunks. Conditioning and output unpacking remain per item.

Verified runtime shape: attention Q/K/V = [2, 56, 19563, 128] for the batched main transformer. Each measured batch completed two model forwards, 50 SA2 calls, 50 SA3 calls and zero attention fallbacks.

The initial adapter kept per-item modulation operations separate. The refined adapter broadcasts matching modality/timestep operations across the two items. Per-item preparation, conditioning assembly and output unpacking still remain separate. This tests one correct experimental batching strategy, not every possible batching or kernel-fusion implementation. Production model code and dependencies were not changed.

3 · Did fewer launches help?

Fewer kernel launches did not translate into a faster pair.

Separate Nsight Systems captures replayed one warm sequential pair and one warm pair for each batch implementation. Their instrumented timings are excluded from the performance averages above.

The refined batched trace has 49.0% fewer kernel events and 49.0% fewer CUDA launch API calls. GPU kernel busy time was 9.84 s for the refined batch versus 9.64 s sequentially. Larger batched kernels still have to process both chunks. The measured launch reduction was not sufficient to produce a warm end-to-end speedup.

Kernel busy time is the union of recorded CUDA execution intervals inside denoising request ranges. Summed launch API time measures time inside CUDA launch calls; it does not cover all Python scheduling overhead, nor can it be subtracted directly from total generation time. These traces do not establish whether compute, bandwidth or a particular kernel is the sole bottleneck.

The unprofiled single-transformer baseline already averaged about 94.7% NVML GPU utilization during denoising. The initial batching implementation averaged about 95.0%; per-run readings for the refinement are included above. That activity reading changed little and does not prove the SMs reached peak arithmetic throughput.

4 · Output correctness and visible differences

All 24 measured videos pass frame and audio checks.

Validated

  • 55 output frames per chunk, 24 fps, 1080×1920 export.
  • Complete video/audio decoding and evenly spaced frame timestamps.
  • Audio/video durations agree within one AAC packet.
  • Decoded audio is identical across configurations and repeats for each input chunk.
  • Both soundtracks align with the correct source slice at zero-sample lag, with correlation above 0.9999 after AAC encoding.
  • All saved video/audio latent tensors are finite.

Not bit-identical visually

Batching changes numerical results despite the same seeds. Batched video SSIM against sequential output ranges from 0.9348–0.9692. Video-latent cosine similarity ranges from 0.9872–0.9971.

The initial and refined batch videos are byte-identical. Two concurrent copies match the sequential videos exactly in these runs.

SSIM is a difference measure here, not a judgment of natural motion or lip-sync quality. Same seeds do not guarantee identical floating-point results when low-precision kernel shapes change. Exported audio is the supplied recording; generated audio latents are not used for the MP4 soundtrack.

5 · Scope and reproducibility

Why there is no new full-video batching result

The requested condition was to test full-video generation if batching helps. It did not improve the warm two-chunk measurements, so a full-video batch run was not launched. The existing approximately 200.3 s best full-video fast result is historical context; these 15–16 s pair timings are not a new measurement of that full video.

Timing protocol

  • One full warm-up pair, then three measured pairs in the same resident processes for each configuration.
  • Existing GPU-prepared text/image/audio conditioning reused identically. Text encoding, initial process startup, lazy checkpoint loading during warm-up and post-run validation excluded from warm timings.
  • Measured interval: first denoise dispatch through both completed, decoded, encoded and saved MP4 files. Latent serialization and queue handoffs included.
  • Private CUDA MPS session for all configurations, 100% active-thread allowance. No concurrent unrelated GPU workloads were observed in the valid runs.
  • Three samples per implementation, in sequential → initial batch → concurrent → refined batch order; no cross-day replication or randomized block design. Small differences should not be generalized.
  • One short matching-length pair tested. Other lengths, larger batches and more fused implementations may behave differently.
Warm-up and excluded attempts

The first sequential attempt stopped during warm-up because the initial ownership monitor did not recognize its own NVENC encoder subprocess. Its timings were excluded; the monitor was corrected to check descendants before the valid matrix. The first NSYS attempt stopped before loading models because profiling adds 2 MiB to the established idle allocation. The retry used the verified 4 MiB profiler idle baseline. Logs are retained in the evidence bundle.
