2 · Why the heavy kernels cannot simply double up

VRAM holds the models. Each SM has a much smaller working area.

A. Both copies really were in GPU memory

At a sample roughly 50 seconds into denoising, both transformer worker processes held about 26.86 GiB each. Two VAE workers were resident too.

Process allocations include model weights, caches and buffers; these are not weight-only measurements. Historical 2T + 2V peak device usage: 68.10 GiB. Encoder preparation happens before the resident stage workers.

B. A heavy block takes 72 of 100 KiB on one SM

An SM is one of the GPU’s 188 compute units. A large transformer matrix-multiply block requests 72 KiB of shared memory inside that unit.

Block A: 72 KiB
28 KiB left
Block B needs another 72 KiB.
72 + 72 = 144 KiB → does not fit in 100 KiB.

The requested allocation is 72 KiB; NCU reports 73 KiB including 1 KiB of overhead. The register limit independently restricts these sampled GEMMs to one block per SM.

One chunk can send enough blocks to occupy the whole GPU

Conceptual diagram, not a measured assignment of blocks to individual SMs. These launches contain thousands of blocks and many waves of work across 188 SMs. A second chunk can interleave, use available tails or share with lighter kernels, but it cannot put two of these heavy blocks on the same SM at the same time.

Registers are another constraint

These heavy GEMMs use 224–254 registers per thread × 256 threads: 57,344–65,024 registers per block, before allocation rounding. Each SM has 65,536 registers.

NCU reports a one-block-per-SM limit from both registers and shared memory for the sampled heavy GEMMs.

What this establishes: the timeline directly measures very little cross-transformer kernel overlap. The resource counters explain why important kernels have limited room to coexist. These measurements support resource contention as a major cause; they do not prove every gap has the same cause or that all possible batching/kernel changes would fail.

Capture setup, validation and limits
  • GPU: RTX PRO 6000 Blackwell Workstation Edition, 96 GB, 188 SMs, 600 W. NSYS 2026.4.1; NCU 2026.2.1.
  • NSYS: CUDA software tracing, NVTX and OS runtime; MPS enabled. GPU metrics at 1 kHz. CPU sampling and context-switch tracing disabled. NVTX sampler boundaries synchronize each worker’s CUDA context.
  • NCU: 22 denoising and 8 decode kernel launch configurations; warmed 55/73-frame shapes, profiled a 73-frame chunk. SpeedOfLight, Occupancy and LaunchStats. Clock/cache control set to none; NCU’s default stable Tensor Core pipeline boost remains in effect.
  • 20 independent original-image anchored chunks, no previous-chunk dependency. 1,186 frames, 24 fps, two steps, seed 9901 + chunk index. Native 736×1280, crop 720×1280, export 1080×1920.
  • All four full NSYS videos passed frame/audio validation and were byte-identical to the historical output. Ownership monitoring recorded zero competing-workload samples.
  • Warm 2T transformer H2D copies totalled ~0.595 GiB and 0.0287 s of GPU copy time across 18 chunks, excluding the first chunk per lane. Repeated full-model transfers are not supported as the main explanation. GPU copy durations exclude CPU API waits.
  • Per-SM block scheduling was not directly traced. The resource diagram is an explanatory inference based on measured kernel attributes, launch sizes and NCU limits. Small kernels and kernel tails can overlap; 1.73 s is not zero.
