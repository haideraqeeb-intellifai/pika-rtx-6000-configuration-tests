Why extra transformer copies did not make H3 faster

Three multi-transformer configurations, one matched control, fresh Nsight Systems captures, and targeted Nsight Compute kernel measurements.

More transformer workers overlapped their requests, but shared the same physical GPU. Each chunk became slower as more workers competed. Small denoising gains were offset by a longer decoding tail. The staged three-transformer case also lost transformer/VAE overlap.

Workload: the same 49.4-second podcast, 20 independent original-image anchored chunks, two Pika Flex steps, 24 fps. All compared runs use default inference mode; the newer 200.3-second fast result is not a matched comparator. Each capture generated and validated the complete video.

2. What went wrong in each configuration

  • 2T + 2V: the denoising span shrank by 8.8 s, but the decoding tail grew by 10.9 s. The full video became 2.5 s slower in the selected runs. A repeat gave the same conclusion.
  • 3T + 1V: denoising finished 14.4 s earlier, but the decoding tail grew by 39.0 s. Only one chunk had completed VAE decoding before the last denoising call finished, versus six with the control.
  • 3T, then 2V: three transformer copies took 120.4 s for their whole phase, versus 121.0 s with the isolated single transformer. Almost no denoising speedup, and sequential stage ordering forfeited the pipeline overlap.

4. Why the important kernels have limited room to overlap

Free VRAM is not the same as free execution resources. The captured transformer GEMMs request 72 KiB of shared memory per block. Each SM has 100 KiB, so two such blocks cannot fit together. Those kernels also use 224–254 registers per thread with 256 threads per block: 57,344–65,024 registers, out of 65,536 registers per SM. A second full transformer copy does not add more SMs, registers, or shared memory.

Recorded kernel resource limits. The GPU has 188 SMs. The large transformer launches have thousands of blocks, enough to occupy the whole device over many waves. Low warp occupancy therefore does not imply enough free resources for another copy of the same heavy kernel. NCU measured approximately 91–94% SM throughput for the sampled transformer matrix kernels and confirmed a one-block-per-SM occupancy limit from both registers and shared memory. Their roughly 16.7% warp occupancy does not mean 83.3% spare compute capacity: those blocks already exhaust the resources needed to admit another large block. 5. What to do with this result

  • Keep the measured 1T+2V layout for this GPU. Extra transformer copies consume memory and stretch per-chunk work without supplying additional hardware.
  • Improve the dominant kernels or reduce repeated VAE launch/setup work before adding more copies. Fast-mode attention and VAE optimization target these costs; their separate measured 200.3-second result is consistent with that approach.
  • Independent physical GPUs can supply additional execution capacity. These one-GPU profiles do not establish eight-GPU scaling or validate greater-than 8× throughput.
